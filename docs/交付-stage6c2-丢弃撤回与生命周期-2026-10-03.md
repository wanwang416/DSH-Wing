## 二、逐项实现

### ① M18 · 纯确认词留痕（拦截但留痕）
- **取舍与依据**（施工单二选一的第 2 项）：纯确认词（嗯/好的/收到/明白/知道了）无信息量，注入只会稀释上下文 → **不注入**；但旧实现只有可选文件 diagLog，logger 零痕迹 = 静默丢弃 → 现 `logger.info("纯确认词留痕 chat=… → 仅回执不注入")` 必打，可核对。
- 落点：`experience.ts` V4 ORDINARY 纯确认分支。
- 旧实现会红：该路径 logger.info 零调用。

### ② M21 · 撤回归属校验（fail-closed，含中期验收三项整改）
- **接线**（中期验收硬项）：`index.ts` createEventHandler 装配处注入 `turnInitiatorOwner: (chatId) => turnInitiator.get(chatId)`——与 5b-2 `initiatorOf` **同一张 turnInitiator Map 同源**，未新建第二张（接线生效测试钉死，见下）。
- **统一 fail-closed**（中期验收指出两分支矛盾，已统一）：**拿不到 operator 或拿不到发起者记录 → 一律拒绝 + warn**，不 cancel。代价权衡：撤回非关键功能，误拒代价 = "撤回不生效"（可控）；误放行代价 = "取消别人的会话"（不可控）。重启后 Map 为空 → 撤回不生效：可接受（agent 通常已随重启销毁，无生成可停）。
- 附带修正：chatId 取值移除 `operator.open_id` 兜底——operator 只做归属校验，不再被当会话 id（防误判）。
- **接线生效测试（本批硬项）**：`stage6c2.test.ts` 源码级断言——createEventHandler 装配必须含 `turnInitiatorOwner: (chatId) => turnInitiator.get(chatId)`，且断言不许出现第二张发起者 Map。
- 攻击场景测试：伪造他会话撤回（operator=ou_stranger ≠ 发起者 ou_alan）→ cancel 不被调 + warn「归属校验拒绝」。
- 旧实现会红：无 operator / 陌生人撤回直接 cancel。

### ③ M38 · cancel cause 合法化
- **合法集合（先列出再改，出处实证）**：`AgentCancelCause = {kind:'user'} | {kind:'parent'} | {kind:'hook', reason: string} | {kind:'disposed'}`——`node_modules/@deepseek-ai/dsh-session/lib/types/types.d.ts` **L118-128**。
- 撤回取消 `{kind:"recalled"}` → **`{kind:"user"}`**（撤回 = 用户主动取消，与 stop 命令、M41 turn 超时同族）；下游识别由用例钉死（`toHaveBeenCalledWith({kind:"user"})`）。
- 旧实现会红：旧值不在合法集。

### ④ M23 · WAL accept 先于 turn 启动
- **病灶（确认）**：queued 分支 accept 在 `serialQueue.enqueue` 回调里，而 `handleUserMessage`（内含 `agent.followup` = turn 已启动）在 enqueue 前同步执行 → accept 晚于 turn 启动，崩溃窗口内 WAL 无记录。
- **修法**：handleInbound 在调用 handleUserMessage **之前**统一 `inboundWal.accept`；steered/stopped、queued、runCommand 三个分支的重复 accept 移除（各分支 delivered 保留在处理成功之后；提问桥/审批/意图桥等提前 return 的消费分支 accept 保留在 L699 之前不受影响）。
- **崩溃窗口断言**：accept 落盘 → 队列任务立即抛错 → 记录仍 `delivered=false`、可重放（stage6c2.test.ts）。
- **WAL 段回收未动证据**：`tests/inbound/wal-stage4.test.ts` 6 用例全绿——M1 旧段回收留 1 段、M1 补空段不写、M2 prune 删除落地、M20 超期清理、M20 保留期防误删、M1 补启动即收敛；`src/inbound/wal.ts` 本批零改动（git diff 可证）。
- 旧实现会红：accept 在 turn 启动之后的时序断言。

### ⑤ M28 收尾 · 生产调用点默认超时
- **取值**：`timeoutMs: cfg.turnTimeoutMs`（默认 600_000，`config/defaults.ts` L92）。
- **依据**：轮次本身有超时（turn-supervisor 同值），出站单条任务不应比整个轮次活得久（施工单判定方式原文）。
- **超时后行为**：`serial.ts withTimeout` reject + `onTimeout` warn + 释放队列后续任务继续——不静默（warn 文案含 key 与超时值，可核对）。
- 测试：源码级断言生产 enqueue 携带 `timeoutMs: cfg.turnTimeoutMs`（非 undefined）+ defaults 同源断言。
- 旧实现会红：生产调用点不传 timeoutMs。
