## 五、各项修复与"旧实现会红"依据

### A1·M1 段回收（wal.ts persistAll）
- 修法：WAL 段与 outbox 段语义不同——**每段即全量快照**（非追加日志），故新段写出成功后所有旧段全部删除（保留最新 1 段）；写新段失败不动任何旧段（对齐 outbox M48"先写成功后删旧段"）；空记录写 0 字节而非 `"\n"`（根除空段）；删除失败逐段 warn + 计数。
- 先红：`tests/inbound/wal-stage4.test.ts`「M1：persistAll 写出新段后…」（旧实现段数 4≠1）、「M1：records 为空时不再写出 1 字节空段」（旧实现内容 `"\n"`）。

### A2·M2 prune 落地防复活（wal.ts persistAll 联动）
- 修法：M1 的新段回收使 prune 后旧段真正消失 → 重启 load 无源可读。
- 先红：同文件「M2：prune 删除落地——prune 后重建实例再 load，记录不复活」（旧实现 pendingCount 复活=1）。
- **坑 1 判断：改实现**。被断言行为"删除后不复活"本应成立，是代码漏了落盘。

### A3·M20 终态清理（wal.ts prune）
- 修法：超保留期一律清理（delivered / 超次 / **过期未投递**），分三类计数 + info 日志。
- 先红：「M20：超期未投递记录被 prune 清理」（旧实现 attempts<2 且 accepted 的过期记录永久滞留）。
- 防误删锚：「M20：保留期内未投递记录不受 prune 影响」——**旧实现下也绿**，有意保留作回归锚。

### B1·M13 dedup 原子写 + 损坏保护（dedup.ts）

### B2·M22 先解析后去重 + chat_type（dispatcher.ts / parser.ts）
- 修法：
  ① handleEvent 中 `dedupe.add` 移到 parseInboundMessage 成功之后；解析失败 warn（含 messageId+msgtype）且不占去重位；
  ② handleParsed（企微入口）msg 已是解析产物，无"先占位后解析"问题，语义不变（用例锚定防回归）；
  ③ parser chat_type 缺失/非法：不再默认 p2p，按 **group 宽松分支**处理 + 经 `__chatTypeUnknown` 标记由 dispatcher warn。**取舍理由**：漏处理（群消息被宽松分支拦）优于越权处理（本应被群策略拦的私聊化处理）；parser 不引 logger 依赖，保持模块纯净。
- 先红：「未知 msgtype → 不占去重位」（旧实现 isDuplicate=true）、「缺 chat_type → warn」（旧实现无 warn 直接当 p2p）。
- **坑 1 判断：改实现**。
