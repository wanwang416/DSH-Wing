## 二、逐条修复说明

### 施工项 1：合批满员丢批（batching.ts）

**修了什么**：满员分支改为 `flush → onFlush → return true`。批次内全部消息（含触发满员的第 8 条）由 onFlush 统一投递，调用方不再单独处理。

**为什么**：旧实现丢弃 flush 返回值后 `return false`，调用方只处理当前一条，批次内前 7 条被取出后直接扔掉（未去重、未落 WAL、无日志）。按提示词确认 return true 是唯一正解：当前条已 push 进 items 尾部，onFlush 用同一 messageId 投递，返回 false 会造成两条路径争抢同一 messageId。

**对齐基底**：阿深已确认接线方案（提示词第三节）。

**回归测试**（先红后绿）：
- `tests/inbound/batching.test.ts` >「超过 maxCount 时整批 flush，返回 true，不丢批次内消息」——旧实现红（`add` 返回 false ≠ true、onFlush 0 次调用），修复后绿
- 同文件 >「满员 flush 后 onFlush 恰好一次且合并文本含全部消息（8 条满员复现）」——旧实现红，修复后绿
- 旧用例「超过 maxCount 时立即 flush 并单独处理」按验收要求一并加强（原来只断言 size()===0）

### 施工项 2：WAL 重放被去重表 100% 拦死 + 假成功日志（dispatcher.ts / index.ts）

**修了什么**：
1. dispatcher 新增 `handleCompensated(event, data)`：与 handleEvent 同一解析+handleInbound 路径，**不做 isDuplicate/add**，返回 `"processed" | "failed" | "dropped"`
2. `index.ts` WAL 重放循环改调 handleCompensated
3. `replayed` 只在 handleInbound 真正成功后计数；`replayed / failed / skipped` 三个数一起打：`入站 WAL 重放：成功 N / 失败 N / 跳过 N`

**为什么**：凡进 WAL 的 messageId 必定已在去重表里（dedupe TTL 24h > WAL 重放窗口 30min），旧实现重放走 handleEvent 必然命中 isDuplicate 被拦，`replayed += 1` 照加 → 日志谎报"重放 N 条"。被拦记录停在 state=replayed / attempts=1，不满足 prune 条件 → 永久驻留。

**对齐基底**：`dsh-lark-link src/application/message-handler.ts:302`——`if (!compensated && !deps.dedupe.add(...))`，补偿重放跳过去重。

**回归测试**（先红后绿）：

- 同文件 >「handleInbound 抛错 → 返回 failed」「非 message 事件 / 无 message_id / 解析失败 → dropped」——新增，绿
- `tests/index.test.ts` >「startBridge：WAL 重放（pendingReplays）→ 重入管线」日志断言更新为新格式「入站 WAL 重放：成功 1 / 失败 0 / 跳过 0」

### 施工项 3：补偿 100% 空转却报"补拉 N 条"（compensation.ts / host/client.ts / index.ts）

**选了 A 方案**（真正实现）：`listMessages` 现在解析 `item.body.content`（JSON 字符串 `{"text":"..."}`）返回 text 字段。理由：改动面小（只扩展返回结构，listMessages 目前只被补偿使用，类型上加 `text?` 兼容旧调用），且 B 方案（删掉死路径）等于放弃断连 10 分钟窗口的补拉能力——A 能真正恢复功能而不是埋掉它。

**同时修了**：`delivered.add` 移到 `reinject` 成功之后——失败不标记已投递，下一轮 onRecovered 可重试（旧实现先 add 再 reinject，失败永不重试）。

**不许假成功**：条目拿不到正文 → 不 reinject、不计数、不标记，打 warn「补偿跳过 …：listMessages 拿不到正文」；结尾汇总「丢消息补偿：N 条因拿不到正文被跳过（未计入补拉数）」。`pulled` 计数只在 reinject 真正成功后增加。

**对齐基底**：`dsh-lark-link src/index.ts:629-636`（onDelivered 在产出落进 outbox 后标记的思路一致）。

**回归测试**（先红后绿）：

### 施工项 4：outbox 瞬时失败永久判死（outbox.ts / index.ts）

**修了什么**（对齐基底 outbox.ts:126-131、286-300 与 config.ts:126-130）：
1. **failed 不进 sentKeys**——只有 done 才进。sentKeys 语义 = "已终结"（幂等拦截只该拦已发出的消息）
2. **重启回队**：rebuildFromDisk 中 failed 与 pending/sending 一样重置为 pending 回队（并去重，同一信封多条历史行只回队一次）
3. **指数退避 + 抖动**：`backoffDelayMs(attempts) = min(60_000, 1000 × 2^(attempts−1))` ±20% 抖动（1s→2s→4s→…→60s 封顶）；`retryDelayMs` 仍可覆盖（旧测试兼容）
4. **maxRetries 缺省 50**（基底 maxAttempts: 50）；`index.ts` createOutbox 显式传 `maxRetries: 50`
5. **fatal 判定**：`isFatalError = /400|403|invalid|not found/i`（基底默认）——429/5xx 一律可重试；`result.retryable === false` 仍立即判死（该语义未动）
6. **死信出口**：`listFailed()` 列举 + `retryFailed()` 手动重放（改回 pending 入队 + 打日志），日志带 failed 计数
7. **pendingCount 只算 pending**——failed 不再虚增 status.json 的 outboxPending（与体检 M3 同源，已一并修）
8. **describeError**：平台返回对象序列化出 `errcode: errmsg`（如 `99991668: too many request`），null/undefined → "unknown"；index.ts 的 deliver catch 已接入（`[object Object]` 根治）

**回归测试**（先红后绿，`tests/outbound/outbox-p0.test.ts` 新文件 7 用例）：
- 「连续 429 → 重试不判死（≥10 轮 attempts、failedCount=0）、重启回队」——旧实现红（3 轮判死）
- 「耗尽 → failed 但 dedupeKey 不进 sentKeys（同 key 可再次 enqueue）、重启回队」——旧实现红（幂等拦截返回原 key）
- 「400/403/invalid/not found 首次尝试即 fatal 不重试」——保护不可重试路径
- 「指数退避 ±20% 区间 + 60s 封顶」（单测 backoffDelayMs 抽样 50 次/档）

- 「describeError 可读化」——旧实现红（不是函数）
