## 二、逐条修复

### ① M8 —— create 成功后流式失败 → 不再新建 inline 卡（改实现）
- **旧实现为何红**：`finalizeToNewCard` 中 `cardkit.create()` 成功（卡片已真正发出、json 已含全文）后，`stream()` 抛错会 fall through 到 inline `sendCard` → 同屏两张卡。测试 `M8：cardkit.create 成功后 stream 失败 → 不再新建 inline 卡` 修复前断言 `sendCard 调用次数 = 0` 实际为 1（红）。
- **修法**：create 成功后的 stream 失败只做**原地重试 1 次**（sequence=2），仍失败则保留占位卡（create 的 json 已含全文，内容不丢），**绝不 fall through**。约 275-289 行"create 失败降级 inline"（正确路径）未动。
- **判断依据（坑 1）**：这是**实现该改**——"create 成功后不重复发卡"这一行为本应成立，是代码漏了分支判定。

### ② M9 —— sequence 在重试中复用（改实现 + 下沉测试）
- **旧实现为何红**：病灶在**两层**：streaming-card 的自增在 sender 层 withRetry 之外（重试复用同一 sequence）；sender 的 `streamCardContent` 收固定数字。测试下沉到真实 PUT 层（`M9：重试链中每次真实 PUT 拿到新 sequence`）修复前只 PUT 1 次即成功（旧实现根本没重试成功过）。
- **修法**：`cardkit.stream` 的 sequence 参数改为 `number | (() => number)` 工厂；streaming-card 传工厂，sender 层 `withRetry` 闭包内每次真实 PUT 调工厂取新值 → 严格递增。
- **判断依据（坑 1）**：**实现该改**——"每次真实 PUT 用新 sequence"是平台强约束，本应成立。
- **契约变更**：`StreamingCardDeps.cardkit.stream` 签名从 `sequence: number` 改为 `number | (() => number)`（向后兼容，数字仍接受）。

### ③ M10 —— 防抖定时器跨 finalize 未清理（改实现 + 加强测试）
- **旧实现为何红**：骨架的两个 M10 用例**当前绿是伪覆盖**（第二笔迟到内容 <30 字符被节流吞掉；快照时序不对）——按坑 1 判断为**该改测试**，加强为两个真正能踩中缺陷的用例：
  - `M10：finalize 前已调度的防抖定时器，finalize 后触发 → 不再 PATCH、不重复 fallback`（修复前：定时器未被清理，runAllTimers 后 patchFull 会二次触发——旧实现此用例红）
  - `M10：finalize 后迟到 addText → 直接被 closed 守卫拒绝`（大内容绕过节流直通 patchAnswer——旧实现红）
- **修法**：新增 `closeForFinalize()`（置 `closed` + 清 `updateTimeout`/`thinkingTimeout`），`finalize()` 与 `finalizeToNewCard()` 入口统一调用；`patchFull`、`schedulePatch`、`addText`、`addThinking`、`addTool`、`setToolResult`、`addContext` 全部前置 `closed` 守卫。
