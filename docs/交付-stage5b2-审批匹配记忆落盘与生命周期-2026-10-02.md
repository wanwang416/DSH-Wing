## 二、各条实现与"旧实现会红"依据

### G6-B（口径修正，非缺陷）
- **改动**：`src/index.ts` — `turnInitiator` Map；`handleInbound` **queued 分支**（真正开 turn 处）快照 `chatId → msg.userId`；`forwarder.onTurnEnd` 清除快照。`approval.ts` — `ApprovalBridgeDeps.initiatorOf?` 新依赖；`answer()` 中 `initiator = deps.initiatorOf?.(chatId) ?? chatId` 传入记忆层。
- **快照点选择依据**：贴件明确"不要用最后一条入站消息的发送者"。queued = 新 turn 起点，steered/插话不覆盖快照（A 触发 turn、B 插话排队时不会误判成 B）；turn 结束即清，防跨 turn 误用。
- **拿不到发起者**（无快照）→ 回退 `chatId`（p2p 等价）；群聊无快照 → 与任何 operatorId 不等 → 不自动放行（fail-closed）。
- **旧格式历史数据**：仍按 5b-1 fail-closed 忽略，未放宽。
- **测试**（`approval-stage5b2.test.ts`，旧实现 = 5b-1"群聊永不命中"或更早"不绑身份"版本必红）：
  1. 攻击场景：群聊老板点 Always → 老板本人再触发 → 自动放行（5b-1 实现必红）
  2. 攻击场景：群聊老板点 Always → 其他人触发 → 仍弹审批（不扩散）
  3. p2p 行为与 5b-1 一致（防回归）
  4. fail-closed：拿不到发起者 → 不自动放行仍弹卡

### M5（改实现）
- **根因**：`onTextInbound` 里 `chatType !== "p2p"` 直接 return false → 群里发的审批提示永远无法被回复命中。
- **修法**：去掉 chatType 硬拒，群聊也消费；**身份校验保持 fail-closed**（operatorId 必须 === wecomBossUserId）。
- **实现中发现并修正的次生问题**：身份校验最初放在决策解析之前 → 群里非老板说句闲聊（非 1-4 决策）也会把老板的审批打成 rejected（**恶意否决也是干预**）。最终顺序 = 先识别决策、后验身份：非决策 → 不消费照常进 agent；是决策且身份不对 → rejected + 留痕。
- **测试**：老板群聊回编号 → 命中结算；非老板决策 → rejected；wecomBossUserId 未配置 → rejected；非决策文本 → 不消费。

### M6（改实现）
- **根因**：`buildApprovalText` 收了 `entryId` 但**文本里根本没显示**；`onTextInbound` 取第一个同 chat pending → 多审批并存必串台（安全问题）。
- **修法**：① 提示文本带编号行 + 用法说明；② 回复解析 `编号[:：\s]*<entryId>` 前缀；③ 编号精确匹配优先；④ 编号不存在 / 属其他会话 → **不结算任何审批** + 提示（fail-closed 不猜）；⑤ 无编号且同 chat 多条并存 → 提示带编号重发，不猜；⑥ 无编号且仅一条 → 兼容旧行为。
- **测试**：同一会话两条并存回 B 编号只结算 B、A 保持待处理（旧实现必红：取第一个会把 B 的回复落到 A）；不存在编号 → 不结算任何 pending；纯数字回复唯一 pending → 放行（兼容锚）。

## 三点五、身份同源说明（G6-B 生效前提，2026-10-02 补）

`shouldAutoAllow` 的比较是**纯字符串相等**——两边必须是**同一身份空间**的值才能命中。

**`initiatorOf` 返回值来源**（实读源码核实，非凭记忆）：

| 平台 | 发起者（initiatorOf 返回） | 来源字段 |
|---|---|---|
| 飞书 | `msg.userId` | `src/inbound/parser.ts` L116：`raw.sender?.sender_id?.open_id ?? raw.operator?.operator_id?.open_id` |
| 企微 | `msg.userId` | `src/inbound/wecom-parser.ts` L159：`senderUserId`（企微 userid） |

**`addAlways` 存入的批准者身份来源**：

| 入口 | 批准者 | 来源字段 |
|---|---|---|
| 飞书卡片点击 | `operatorOpenId` | `src/inbound/event-handler.ts` L55/96-98：事件 `operator.operator_id.open_id` |
| 企微文本回复 | `ctx.operatorId` | `src/index.ts` L648：传 `msg.userId`（= 企微 parser userid） |

**同源保证**：飞书侧发起者与批准者都取自飞书 `open_id`（同一身份空间）；企微侧两路都取自企微 `userid`（同一身份空间）。同一平台内同值可命中；跨平台值域不相交（`ou_*` openId ≠ userid），天然不会误命中。

**不混入 chatId**：`answer()` 里的 chatId 仅在**无快照的 p2p 回退**时充当发起者（p2p 下 chatId ≡ 归属者身份，由 parser 保证）；记忆键不含 chatId 作身份——5b-1"群聊用 chatId 顶替身份导致永不命中"正是要修的根因，B 口径已改。

**测试钉死（3 条，`approval-stage5b2.test.ts`）**：
1. 同源同值命中：老板发起（快照=openId）→ 老板点卡（同值）→ 再触发命中免问
2. 跨平台交叉：飞书 openId 批准的记忆 → 企微 userid 发起 → **不命中仍弹卡**（不是误命中）
3. 反向隔离：身份集混入企微 userid 后 → 其他身份发起 → 不命中（身份集语义 = 逐个精确比对，不做前缀/模式匹配）
