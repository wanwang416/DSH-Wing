## 二、逐项实现与量化证据

### M28 · 串行队列超时
- 实现：`src/session/serial.ts` `enqueue(key, task, opts?)` 增加可选 `{ timeoutMs, onTimeout }`；超时任务 reject（错误含 key 与超时值）+ `onTimeout` 回调（日志/计数挂点），**队列立即释放**，后续任务继续。**不传 timeoutMs = 旧行为**（现有唯一调用点 index.ts L712 暂未配超时——是否给生产 turn 配默认值属 6c/6d 入站语义域，本批不越界，见 §七）。
- 超时 timer 带 `unref()`：任务挂起、超时未到期间**不阻止宿主退出**（unref 是设计的一部分，见 §六返工说明）。
- 旧实现会红：一条 `new Promise(() => {})` 永挂任务 → 旧实现后续任务 `secondRan` 永远 false。
- 用例：`tests/session/stage6b-limits.test.ts`「一条任务永久挂起 → 真实超时释放队列」（**真实时钟 30ms 超时 + 100ms 真实等待**，不依赖 fake timers——阿深可独立复跑验证）+「未超时任务不受影响」。

### M41 · turn 超时先 cancel 再 dispose
- 实现：`src/index.ts` onTimeout 重写。查证结论：agent handle **有原生 `cancel(cause, options)` 接口**（`src/session/mapper.ts` L92 `AgentHandleLike.cancel`、`src/agent/caller.ts` L186/L272 直通 SDK `agent.cancel`，SDK 侧取消后收敛到 idle、上下文保留）。顺序：先 `h.cancel({kind:"turn_timeout"})` + warn「上下文保留」→ return；**cancel 抛错或不可用 → 降级 dispose**（兜底保留：超时后锁必须释放，否则卡住下一轮）。
- 旧实现会红：dispose 被直接调用（上下文丢失）。
- 用例：「可取消 → 走 cancel、不走 dispose」「cancel 抛错 → 兜底 dispose 仍执行」。

### M43 · 空闲清理计时依据（复核结论：**确有误删窗口 → 已修**）
- 复核证据（代码行）：
  1. SDK 类型 `node_modules/@deepseek-ai/dsh-agent/lib/types/runtime-types.d.ts` L45：`AgentStatus = 'idle' | 'running'`，且 **L91 注释明示"maintenance task 运行期间 public status 保持 idle"** —— 体检报告"只按最后一条入站计时"的说法被证实，且比报告说的更糟：连 status 守卫也防不住维护任务窗口；
  2. `src/session/mapper.ts`：`idleAt` 只在创建（L119）与 map 命中（L130）时更新——**turn 结束不刷新**。30 分钟 ttl 一到，哪怕 agent 刚跑完一个长 turn 也会被清（上下文丢失）。
- 修法：mapper 增 `touch(chatId)`（刷新 idleAt，仅对存在的 chat）；`src/index.ts` `onTurnEnd` 接线 `mapper?.touch?.(chatId)`。清理语义不削弱：真空闲（超 ttl 且未 touch、status=idle）仍被清。
- 用例：「turn 结束 touch 后 → 空闲清理不误删」（旧实现必红：removed=1）+「真空闲仍被清理」。

### M4 · lastError 永不清理
- 实现：`src/host/status.ts` `setConn`：`state === "connected"` 时 `delete status.lastError`。浅合并下 `{lastError: undefined}` 不会覆盖旧值，必须 delete；`WingStatus` 补 `lastError?: string` 类型字段。
- 量化对比（用例内断言）：改前 `setConn("connected")` 后 `lastError === "连接失败（第 1/5 次）"`（残留）；改后 `=== undefined`。真机效果（待 ALAN 重启后验证）：面板/`status.json` 在连接恢复后不再显示旧错误。
- 旧实现会红：恢复后 lastError 残留。用例：「失败（有 lastError）→ 成功 → lastError 被清」。

### M12 · outbox 容器上限
- **sentKeys 上限**：`sentKeysLimit`（默认 **5000**；取值理由：去重键约 50-80B/条 × 5000 ≈ 400KB 内存封顶；按高频桥的量级 5000 条远超 7 天 retainDays 窗口内的已终结消息数，重启后 sentKeys 从盘上段重建，淘汰窗口外旧键不影响重启防重发语义）。FIFO 淘汰（Set 插入序）；投递成功后自动 trim；触发时 info 日志含「淘汰 N 条 / 上限 / 现存」计数。
- **终态信封清理**：`清理终态信封(retentionMs)`（默认 **24h**，`envelopeRetentionMs` 可配）只清 `status==="done"` 且 `updatedAt` 超期的条目——**pending/sending/failed 绝不触碰**；info 日志含清理条数与现存数。段文件在盘上仍全量保留（M46 语义不变），清理只影响内存容器。
- 旧实现会红：150 键全留（无上限）/ done 超期不清。
- 用例（`tests/outbound/stage6b-outbox.test.ts`，黑盒口径走公开 API）：
  - 「投递成功超过上限 → 旧键被淘汰、最近键仍在 + 日志留痕」
  - 「无上限参数时用默认 5000（不传参数行为不回归）」
  - 「真实投递流：done 信封超期被清；**在途信封绝不清理（红线，直接断言条目存在）**」
  - 「★ M46/M47/M48 防回归：清理后 failed 保留语义不变」
